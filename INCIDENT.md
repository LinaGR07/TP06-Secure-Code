# Rapport d'incident : version compromise de `requests`

**Scénario (fictif) :** la version de `requests` utilisée par MiniShop (`2.34.2`) est annoncée comme compromise. Elle contient du code malveillant qui s'exécute dès qu'on l'importe et qui peut voler des secrets.

## 1. Détection

L'alerte peut venir de plusieurs sources :
- le workflow `security` tourne **tous les jours à 6 h** : le job `pip-audit` passe au rouge dès que l'avis est publié ;
- **Dependabot** ouvre une alerte de sécurité sur le dépôt ;
- un avis publié (GitHub Advisory, CVE, PyPI qui retire la version).

On confirme en local :

```bash
pip-audit -r app/requirements.txt
```

## 2. Évaluation de l'exposition

**Est-ce qu'on utilise cette version ?**

```bash
grep -A3 "^requests==" app/requirements.txt              # locked version and its hashes
git log --oneline -S "requests==2.34.2" -- app/requirements.txt   # since when
```

**Est-ce qu'on a installé le fichier piégé ?** On compare les hashes du `requirements.txt` avec ceux donnés dans l'avis. Comme on installe avec `--require-hashes`, pip refuse tout fichier dont le hash ne correspond pas. Si les hashes sont différents, le fichier malveillant n'a pas pu être installé.

**Où tourne-t-elle ?**

```bash
# SBOM generated by the CI
gh run download <run-id> -n sbom
jq -r '.components[] | select(.name=="requests") | .version' sbom.cdx.json

# Docker image
docker run --rm --entrypoint pip minishop show requests

# Local venv
pip show requests
```

**Qu'est-ce qui a pu être volé ?**
- **Conteneur** : la `SECRET_KEY` et la base de données (mots de passe hachés en argon2).
- **CI** : peu de risque, la `SECRET_KEY` y est factice et le jeton GitHub est en lecture seule.
- **Postes des développeurs** : clés SSH, jetons GitHub, fichier `.env`.

## 3. Confinement

```bash
# Keep a copy for analysis, then stop the container
docker save minishop -o minishop-incident.tar
docker stop <container>
```

On bloque la version dans `app/requirements.in` :

```
requests!=2.34.2
```

On ne déploie plus rien tant que la correction n'est pas validée.

## 4. Correction

```bash
cd app
pip-compile --upgrade-package requests --generate-hashes --strip-extras requirements.in
cd ..

# Recreate the venv: it ran malicious code
rm -rf .venv && python3 -m venv .venv && source .venv/bin/activate
pip install --require-hashes -r app/requirements.txt
pip install pytest pip-audit

pip-audit -r app/requirements.txt
pytest -q tests

# Rebuild the image without reusing the old layers
docker build --no-cache -t minishop app

git commit -am "fix(deps): exclude compromised requests 2.34.2"
git push
```

On attend que la CI soit entièrement verte avant de redéployer.

## 5. Rotation des secrets

Tout secret auquel le code malveillant avait accès est considéré comme volé. On les change **après** la correction, sinon le code malveillant volerait aussi les nouveaux.

- **`SECRET_KEY`** : on en génère une nouvelle. Tous les anciens cookies de session deviennent invalides.
  ```bash
  python -c "import secrets; print(secrets.token_hex(32))"
  ```
- **Mots de passe des utilisateurs** : réinitialisation, au moins pour les comptes admin.
- **Postes des développeurs** : nouvelle clé SSH, nouveaux jetons GitHub.
  ```bash
  gh auth logout && gh auth login
  ssh-keygen -t ed25519
  ```

## 6. Retour d'expérience

**Ce qui a aidé :**
- le **lockfile avec hashes** : on sait exactement quel fichier est installé ;
- le **SBOM** : on sait tout de suite quelle version tourne et où ;
- **pip-audit tous les jours** dans la CI : détection automatique ;
- les **secrets hors du code** : il suffit de changer une variable d'environnement ;
- le **conteneur non-root** et la **CI en lecture seule** : le code malveillant a moins de pouvoir.

**À améliorer :**
- le lockfile ne protège pas si la version était **déjà piégée** au moment où on l'a verrouillée : il faudrait attendre quelques jours avant d'adopter une nouvelle version ;
- bloquer le trafic sortant du conteneur, pour empêcher l'envoi des données volées ;
- écrire une procédure d'incident à l'avance.

**Exemple réel :** en mars 2026, les tags de l'action GitHub `trivy-action` ont été réécrits vers un code qui volait des secrets. C'est pour ça que notre CI épingle chaque action par **SHA de commit** au lieu d'un tag.
